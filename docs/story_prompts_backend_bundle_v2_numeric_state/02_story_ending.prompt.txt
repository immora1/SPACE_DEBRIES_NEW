## 参考优先级

生成结局时依次参考：

1. `selected_ending`：后端已确定的结局方向，必须完整执行
2. `current_node` 和 `previous_handoff`：决定结局从哪里继续、需要回收什么
3. `story_state`、`key_outcomes` 和 `active_consequences`：决定结局中的完整程度、缺口和持续影响
4. `story_context` 和 `known_to_user`：保持核心事件、异常机制和已有事实一致
5. `selected_game_answers`：使用后端确认的六道轨道事件结果理解最终一次操作的实际影响，不提及题号、按钮或界面

不得因低优先级内容较长而忽略高优先级内容。

## 当前任务

1. 使用 `selected_ending.ending_id` 和 `selected_ending.outcome` 完成结局。

结局已由后端根据累计数值和持续后果选定。不得重新选择、修改或创造其他结局，也不得为了追求戏剧性改变已发生事实。

2. 从 `previous_handoff.current_situation` 之后继续，完成 `current_node.summary` 和核心事件，明确呈现：

- `user_expectation` 最终是否实现
- `irreplaceable_part` 中哪些部分被保留、改变或失去
- 关键物件、动作和约定的最终结果
- `key_outcomes` 与 `active_consequences` 如何影响最终过程
- 用户与核心人物最终停留的关系状态

`story_state` 中的数值均为后端确认后的最终累计值：

- 较高的 `event_integrity` 应对应更多核心内容被保留
- 较高的 `relationship_connection` 应对应更充分的理解、信任或共同完成
- 较高的 `uncertainty` 应保留更多无法完全确认的细节或结果缺口

数值只用于控制结局细节，不得在正文中直接展示，不得修改或重新计算。

3. 完成细节与情感收束：

- 回收 `previous_handoff.unresolved_threads` 中与核心事件有关的问题
- 已出现的重要物件、承诺和动作必须得到明确结果
- 出现对白、回忆或交代时，写出具体内容，不用“说了几句”“谈起往事”等模糊表达代替
- 通过心理感受、动作、目光、停顿、呼吸和具体对白呈现人物的即时反应
- 不用“很稳”“很轻”“很坚定”“目光复杂”等评价式词语替代可观察细节
- 让人物关系形成明确的情感落点，不再留下新的主要悬念

4. `story_text`：

- 控制在450至700个中文字符
- 使用4至6个自然段
- 遵守 System Prompt 的叙事语言、视角和节奏要求
- 每段承担明确的收束作用
- 至少包含两处能够具体感受到人物情绪的可观察细节
- 以具体动作、对白、感官和物件变化完成故事
- 避免不必要的“但、却、只是、然而”等转折
- 不再制造新的主要冲突
- 可以保留已经形成的遗憾，不得临时增加悲剧
- 不解释异常的真实技术原因
- 不生成选项、分支或知识说明

5. `ending_summary` 用1至3句话概括核心事件结果、不可替代部分的保留情况和人物关系状态。

6. `next_node_context` 用1至3句话总结故事中实际出现的异常现象、异常造成的影响和尚未解释的原因，不展开技术解释。
